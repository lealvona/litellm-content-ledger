litellm-content-ledger · for LiteLLM proxy operators

A flight recorder for every model call through your proxy.

When an agent receives something strange, we should be able to read exactly what the provider sent. The content ledger keeps the full request and response of every proxy call, off the request path, redacted, compressed and kept for as long as your retention policy says.

MIT licensed · measured on LiteLLM 1.92.0
Why this exists

One call, 19,900 characters nobody could explain

An agent received a reply full of looping text, a garbled hostname and a fake "out-of-band user message". The agent's own safety check blocked it and the agent stopped. When we went to the proxy to check what the provider actually returned, the proxy had kept the timing and the token count. It had not kept a single word.

How it works

Tap the gateway, never slow it down

When agents reach their models through one LiteLLM proxy, every request and response passes through that one place. The ledger is a small callback inside that proxy. It does almost nothing on the request path, and every expensive step runs later, in a separate process. Select a stage to read what it does.

Six benchmark runs

How the design got here

The first version looked fine on paper and failed the measurement. Each run below either exposed a cost or proved a fix.

Run 1
+33 ms p50 on large callsRedaction inside the proxy was the cost.

Serializing a 151 KB record took 0.026 ms. The secret-redaction regexes took 21.9 ms, and Python's regex engine holds the interpreter lock, so even a background thread stalled the proxy. Redaction moved to the hourly ship job, a separate process.

Run 2
discardedThe benchmark measured the wrong processes.

Run 1's proxies had not shut down, so two arms of run 2 talked to old servers. The script now stops proxies by port and refuses to start if a port is busy.

Run 3
+19 ms on failuresSuccess paths flat, error replies slower.

LiteLLM waits for logging callbacks before it sends an error response, so this is the path that shows any delay.

Runs 4–5
diagnosisNot the handler, not "any second callback".

A control proxy with two ordinary callbacks added about 1 ms. Timing inside the real proxy put the handler at 0.18 ms. The remaining suspect: waking the writer thread on every call made it fight for the interpreter lock while the error reply was being built.

Run 6
within noise at p50 / p95The writer wakes on a timer instead.

Calls only enqueue; the writer drains everything once a second. The failure penalty disappeared at p50 and p95, which confirmed the diagnosis.

Sized from real traffic

Six months fits easily under the cap

On the agent deployment it was built for, the proxy handled 4 to 1,557 requests a day, and one agent sent 95 % of all prompt tokens. Agents resend their whole conversation every turn, which sounds expensive, but compressed full records stay small. Estimates use 3.32 bytes per token, measured on that agent's own text, and per-record zstd ratios measured on real content. Hourly batches with zstd -19 should come in lower still.

Each one has a test that fails without it

What the ledger guarantees

Logging can never break a request

A full queue or a full spool drops the record and counts it. Every error is caught. Drop counts reach your notifiers so a gap is visible.

Provider keys are never recorded

LiteLLM hands every callback the raw upstream API key. The record is built field by field and never reads it.

Agents cannot switch it off

A client could send "no-log": true to skip every logger. global_disable_no_log_param closes that, and the record notes that the client asked.

Secrets are redacted before data leaves the spool

Bearer tokens, sk- keys, AWS, GitHub, Slack and Google keys, JWTs, private-key blocks and password assignments become [REDACTED:rule]. Personal details stay, because the content is the forensic record.

Nothing is deleted until the copy is proven

A spool file is removed only after its compressed copy's sha256 matches in the store. A mismatch keeps everything for the next run.

Shipped files are never overwritten

If a file of the same name already exists with different content, the new one gets a hash suffix instead.

The root disk stays safe

By default the writer refuses a spool on the root filesystem. A full root disk takes databases down with it.

Private by default

Spool and store directories are 0700 and files 0600. Nothing is served over HTTP and no cloud service is involved.

114 tests. A mutation check breaks 26 guarantees in the source one at a time; the tests catch all 26. An end-to-end run against a real NAS shipped, verified, read back and expired a test record.

Get started

Four steps

Install with pipx install git+https://github.com/lealvona/litellm-content-ledger. Enabling the callback needs one proxy restart.

  1. content-ledger install-callback /path/to/litellm-config-dir
  2. Add content_ledger.proxy_handler_instance to callbacks and set global_disable_no_log_param: true.
  3. Copy examples/profile.toml to ~/.config/content-ledger/profile.toml and set the store and retention.
  4. Restart the proxy and enable the ship, retain and health timers from deploy/systemd.

Rollback is one line: remove the callback and restart. Have your agents send x-litellm-session-id so fcl trace can replay a whole conversation instead of single calls.
